# Specification: Subagent Dispatch System

## 1. Objective
To implement a mechanism where a primary agent can delegate a specific task to a temporary, isolated subagent. The subagent operates in its own context, can utilize the same toolset as the primary agent, and returns a final synthesized result to the primary agent upon completion.

## 2. Tool Definition: `DispatchSubAgent`
A new tool will be registered and made available to the agent.

**Parameters:**
- `prompt` (string): The specific task or question the subagent needs to address.
- `files` (list of strings): A list of file paths that should be read and injected into the subagent's initial context.
- `systemPrompt` (string, optional): Optional override or addition to the default system prompt to give the subagent a specific role (e.g., "You are a security auditor").

**Return Value:**
- The final string response generated by the subagent.

## 3. Execution Flow
When the `DispatchSubAgent` tool is invoked:

1.  **Context Initialization**:
    - A new, empty conversation session is created.
    - The system prompt is applied.
    - The requested `files` are read from the disk and injected into the context as "Context Documents" (replicating the logic used in the current `GetIndexContents` flow).
2.  **Subagent Loop**:
    - The `prompt` is sent to the LLM.
    - The subagent enters a standard Agent Loop:
        - If the subagent calls a tool $\rightarrow$ execute tool $\rightarrow$ feed result back to subagent.
        - Repeat until the subagent provides a final answer.
3.  **Termination**:
    - The subagent's final response is captured.
    - The subagent's isolated session is disposed of.
4.  **Integration**:
    - The captured response is returned as the result of the `DispatchSubAgent` tool call to the primary agent.

## 4. Key Technical Requirements

### A. Context Isolation
- The subagent must **not** have access to the primary agent's conversation history.
- The subagent starts with a "clean slate," containing only the injected files and the specific prompt.

### B. Recursive Tool Capability
- The subagent must be registered with the same `ToolProvider` (or a clone of it) as the main agent.
- **Recursion Policy**: We must decide if a subagent can dispatch another subagent (Nested Subagents). *Recommendation: Allow it, but implement a maximum depth limit (e.g., 3 levels) to prevent infinite loops.*

### C. File Injection Mechanism
- Reuse the existing file-reading logic.
- The injected files should be presented to the subagent as: `File: <path>\nContent: <content>`.

## 5. Edge Cases & Constraints
- **Token Limits**: If the primary agent requests too many files for the subagent, the subagent may hit context limits immediately. We should implement a check or a warning.
- **Timeouts**: Subagents should have a maximum execution time or a maximum number of iterations to prevent the primary agent from hanging indefinitely.
- **Error Handling**: If the subagent crashes or fails to reach a conclusion, the tool should return a descriptive error message to the primary agent (e.g., `"Subagent failed to complete the task: [Error Details]"`).
